我们现在都是怎么工作的?说起来好笑(或者说可悲),但基本上就是:ask agent → hope(问智能体 → 祈祷)
其实不必如此。一位备受尊敬的开发者(《Total TypeScript》的作者)把随意的提示词变成了一套可重复的工程流程,并设置了智能体必须通过的检查点。

这是什么意思?不是给一个巨大的提示词,而是根据你所处的阶段运行一个定义好的 workflow:

如果你有一个模糊的想法,或者一个还不成熟的功能:`/grill-me`,然后 `/to-spec`
智能体会质疑你的假设,然后写出一份真正的 spec。

如果已经有了 spec,但任务太大没法直接构建:`/to-tickets` 或 `/wayfinder`
你会得到小而聚焦的 ticket,或者一张存在于 GitHub 或 Linear 中的决策地图。

如果你已经准备好构建:`/implement` 配合 `/tdd`
一次推进一小块,red → green → refactor,而不是一下子重写半个应用。

如果构建完了但有东西坏了:`/diagnosing-bugs`
复现问题 → 缩小范围 → 提出假设 → 添加度量 → 修复。

合并(merge)之前:`/code-review`
检查同时沿两个维度进行:是否符合标准,以及是否与 spec 相符。

这样你就能让 AI 对你更加专注,使用了解模型和智能体局限的命令,而且还能让你长期保持在边界之内,不会跳步、遗忘或疲惫。

这会让智能体表现得更像和你一起工作的资深开发者,先要求澄清、拆解、测试和 review,而不是像一个立刻开始写代码的初级开发者。

也就是说,你不会跳过对齐预期、界定 scope、测试和 review 这些"枯燥的部分",而这些在 vibe coding 时通常会丢失。

但要记住的是,这不是魔法……这是被打包进 skills 里的流程(process)。
流程中最重要的部分是你。记住这些命令,背熟它们,并在合适的时候使用。
这一点没有任何模型和任何 skill 能替你做到。

如果你跳过了用 `/setup-matt-pocock-skills` 做的初始设置,或者干脆没有真正使用斜杠命令,那它不过是又一个装着 Markdown 文件的文件夹。

顺便说一句,如果你已经有自己的 skills 和命令,值得让聊天梳理一下它的命令,看看你已经有什么、哪些值得采用。
